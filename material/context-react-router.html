React: Context API y React Router 🚀

Manejando el estado global y la navegación en tu aplicación.

Parte 1: Context API (El "Walkie-Talkie" de React) 📢

Resuelve el problema del "Prop Drilling" (perforación de props), permitiendo que un componente "Abuelo" pase datos a un "Nieto" directamente, sin que el "Padre" tenga que actuar como intermediario.

Ejemplo: Un Switch de Tema (Dark/Light Mode)

Paso 1: Crear el Contexto (`ThemeContext.js`)


import { createContext } from 'react';
export const ThemeContext = createContext('light');

Paso 2: Proveer el Contexto (`App.js`)


import React, { useState } from 'react';
import { ThemeContext } from './ThemeContext';
import Navbar from './Navbar';

function App() {
  const [theme, setTheme] = useState('light');
  const toggleTheme = () => {
    setTheme(theme === 'light' ? 'dark' : 'light');
  };

  // 🚨 PROBLEMA: Este objeto { theme, toggleTheme } se crea
  //    NUEVO en CADA renderizado de App.
  return (
    <ThemeContext.Provider value={{ theme, toggleTheme }}>
      <div className={theme === 'light' ? 'bg-light' : 'bg-dark'}>
        <Navbar />
        {/* ...más contenido... */}
      </div>
    </ThemeContext.Provider>
  );
}

Paso 3: Consumir el Contexto (`Navbar.js`)


import React, { useContext } from 'react';
import { ThemeContext } from './ThemeContext';

function Navbar() {
  const { theme, toggleTheme } = useContext(ThemeContext);
  // ... resto del componente ...
}

Parte 1.5: Optimizando Context con `useMemo` y `useCallback`

El Problema de Rendimiento:
Cada vez que el componente `App` se re-renderiza, crea un objeto value nuevo. React ve este objeto "nuevo" y fuerza a todos los componentes que consumen el contexto (Navbar) a re-renderizarse, incluso si `theme` no cambió.

Para solucionar esto, "estabilizamos" el valor con useMemo y useCallback, que sirven para memorizar (cachear) valores y funciones.

  • useCallback(fn, [deps]): Memo-iza (guarda) una función. Solo la crea de nuevo si sus dependencias `[deps]` cambian.
  • useMemo(() => valor, [deps]): Memo-iza (guarda) un valor (un objeto, un array, un cálculo). Solo lo recalcula si sus dependencias `[deps]` cambian.

Ejemplo: Estabilizando nuestro `ThemeContext`


import React, { useState, useMemo, useCallback } from 'react';
import { ThemeContext } from './ThemeContext';
// ...

function App() {
  const [theme, setTheme] = useState('light');

  // 1. Estabilizamos la FUNCIÓN con useCallback.
  const toggleTheme = useCallback(() => {
    setTheme(t => (t === 'light' ? 'dark' : 'light'));
  }, []); // <-- Sin dependencias, la función nunca cambia

  // 2. Estabilizamos el OBJETO 'value' con useMemo.
  const value = useMemo(() => ({
    theme,
    toggleTheme
  }), [theme, toggleTheme]); // <-- Solo se recalcula si theme o toggleTheme cambian

  // Ahora 'value' es estable. Los hijos solo se re-renderizarán
  // si el valor 'theme' realmente cambia.
  return (
    <ThemeContext.Provider value={value}>
      {/* ... */}
    </ThemeContext.Provider>
  );
}

Parte 2: React Router DOM (El "Navegador GPS" de React) 🗺️

React Router es una librería que simula la navegación en una "Single Page Application" (SPA). Observa la URL y renderiza diferentes componentes **sin recargar la página**.

Componentes Clave

  • <BrowserRouter>: Envuelve toda tu aplicación (en `main.jsx`).
  • <Routes>: Define el área donde cambiarán las páginas.
  • <Route path="..." element="..." />: La regla de navegación.
  • <Link to="...">: Reemplaza a <a href> para navegar sin recargar.

Hooks Clave

  • useParams(): Lee parámetros dinámicos de la URL (ej. /user/:id).
  • useNavigate(): Permite redirigir al usuario (ej. después de un login).

Ejemplo: Definir Rutas (`App.js`)


import React from 'react';
import { Routes, Route } from 'react-router-dom';
import Navbar from './Navbar';
import HomePage from './pages/HomePage';
import AboutPage from './pages/AboutPage';

function App() {
  return (
    <div>
      <Navbar /> {/* Se muestra en TODAS las páginas */}
      <div className="container mt-4">
        <Routes>
          <Route path="/" element={<HomePage />} />
          <Route path="/about" element={<AboutPage />} />
        </Routes>
      </div>
    </div>
  );
}

Parte 3: Tópico Avanzado - Combinando Context y Router para Rutas Protegidas 🛡️

Este es el caso de uso perfecto que une ambos conceptos. ¿Cómo hacemos para que la ruta /admin solo sea accesible si el usuario tiene el rol de "admin"?

Usaremos el Context API para saber *quién* es el usuario, y React Router para decidir *dónde* puede ir.

Paso 1: Crear un `AuthContext`

Primero, creamos un contexto para manejar la autenticación. Este contexto proveerá la información del usuario y funciones para `login` y `logout`.


// contexts/AuthContext.js
import React, { createContext, useState, useContext, useMemo, useCallback } from 'react';

// 1. Crear el contexto
const AuthContext = createContext(null);

// 2. Crear el Proveedor (el componente que maneja el estado)
export function AuthProvider({ children }) {
  const [user, setUser] = useState(null); // 'null' significa que nadie está logueado

  // Función de login (simulada)
  const login = useCallback((username, role) => {
    setUser({ username, role });
  }, []);

  // Función de logout
  const logout = useCallback(() => {
    setUser(null);
  }, []);

  // 3. Estabilizar el 'value' con useMemo
  const value = useMemo(() => ({
    user,
    login,
    logout
  }), [user, login, logout]);

  return (
    <AuthContext.Provider value={value}>
      {children}
    </AuthContext.Provider>
  );
}

// 4. Crear un hook personalizado para consumir el contexto fácilmente
export const useAuth = () => {
  const context = useContext(AuthContext);
  if (!context) {
    throw new Error('useAuth debe ser usado dentro de un AuthProvider');
  }
  return context;
};

Paso 2: Crear el Componente ``

Este es el "guardia de seguridad". Es un componente que envuelve a nuestras rutas.

  • Revisa el `AuthContext`.
  • Si el usuario tiene permiso, renderiza la página (children).
  • Si no, lo redirige usando el componente <Navigate> de React Router.

// components/RutaProtegida.js
import React from 'react';
import { Navigate, useLocation } from 'react-router-dom';
import { useAuth } from '../contexts/AuthContext';

// Recibimos un 'roleRequerido' (ej. "admin")
export function RutaProtegida({ children, roleRequerido }) {
  const { user } = useAuth();
  const location = useLocation();

  // 1. ¿El usuario NO está logueado?
  if (!user) {
    // Redirigir al login. Guardamos la página que intentaba visitar.
    return <Navigate to="/login" state={{ from: location }} replace />;
  }

  // 2. ¿Se requiere un rol específico Y el usuario NO lo tiene?
  if (roleRequerido && user.role !== roleRequerido) {
    // Redirigir a una página de "No Autorizado" o al inicio.
    return <Navigate to="/no-autorizado" replace />;
  }

  // 3. Si todo está bien, muestra la página solicitada.
  return children;
}

Paso 3: Actualizar las Rutas (`App.js`)

Finalmente, envolvemos nuestras rutas con el componente <RutaProtegida>.


import React from 'react';
import { Routes, Route } from 'react-router-dom';
import Navbar from './Navbar';
import HomePage from './pages/HomePage';
import LoginPage from './pages/LoginPage';
import AdminDashboard from './pages/AdminDashboard';
import PerfilPage from './pages/PerfilPage';
import NoAutorizadoPage from './pages/NoAutorizadoPage';
import { RutaProtegida } from './components/RutaProtegida';

function App() {
  return (
    <div>
      <Navbar />
      <div className="container mt-4">
        <Routes>
          {/* Rutas Públicas */}
          <Route path="/" element={<HomePage />} />
          <Route path="/login" element={<LoginPage />} />
          <Route path="/no-autorizado" element={<NoAutorizadoPage />} />

          {/* Ruta solo para usuarios logueados (cualquier rol) */}
          <Route 
            path="/perfil" 
            element={
              <RutaProtegida>
                <PerfilPage />
              </RutaProtegida>
            } 
          />

          {/* Ruta solo para rol "admin" */}
          <Route 
            path="/admin" 
            element={
              <RutaProtegida roleRequerido="admin">
                <AdminDashboard />
              </RutaProtegida>
            } 
          />
          
        </Routes>
      </div>
    </div>
  );
}

Parte 4: Seguridad en el Almacenamiento de Datos del Cliente 🔐

Cuando guardamos información en el navegador del usuario (cliente), debemos ser muy cuidadosos, especialmente si son datos sensibles como tokens de sesión.

El Problema Principal: Ataques XSS

El mayor riesgo es el **Cross-Site Scripting (XSS)**. Ocurre cuando un atacante logra inyectar código JavaScript malicioso en tu página web (por ejemplo, a través de un comentario no sanitizado).

Si guardas datos en lugares accesibles por JavaScript, ¡ese script malicioso podría robarlos!

Opciones de Almacenamiento y Sus Riesgos

1. `localStorage`

  • Pros: Muy simple de usar, persiste incluso si cierras el navegador.
  • Contras: Totalmente vulnerable a XSS. Cualquier script en tu página puede leer y escribir en él.
  • Uso Seguro: Solo para datos **no sensibles**, como preferencias del usuario (ej: tema oscuro/claro), datos de caché que no importan si se pierden o se leen.
Nunca guardes tokens de sesión, datos personales o cualquier cosa sensible en `localStorage`.

2. `sessionStorage`

  • Pros: Similar a `localStorage`, pero los datos se **borran automáticamente** cuando se cierra la pestaña o el navegador.
  • Contras: Igualmente vulnerable a XSS mientras la pestaña está abierta.
  • Uso Seguro: Para datos temporales no sensibles que solo necesitas durante la sesión actual de la pestaña.

3. Cookies HTTP (con Banderas de Seguridad) 🍪

  • Pros: ¡Pueden ser mucho más seguras si se configuran correctamente desde el servidor!
  • Banderas Clave:
    • HttpOnly: ¡La más importante! Impide que JavaScript acceda a la cookie. Esto mitiga enormemente el riesgo de XSS para robar tokens.
    • Secure: Asegura que la cookie solo se envíe a través de conexiones HTTPS (encriptadas).
    • SameSite=Strict o SameSite=Lax: Ayuda a prevenir ataques CSRF (Cross-Site Request Forgery).
  • Contras: Requieren **configuración en el servidor** (backend). No puedes poner la bandera `HttpOnly` solo desde el frontend.
  • Uso Seguro: La forma recomendada para almacenar tokens de sesión sensibles. El servidor envía la cookie `HttpOnly` al cliente después del login, y el navegador la enviará automáticamente en las siguientes peticiones al mismo dominio.

4. Memoria de JavaScript (Estado de React)

  • Pros: La opción más segura en el cliente, ya que los datos viven solo en la memoria de la aplicación mientras se ejecuta. No es directamente accesible por otros scripts maliciosos de la misma forma que `localStorage`.
  • Contras: No es persistente. Los datos se pierden si el usuario refresca la página o cierra la pestaña.
  • Uso Seguro: Ideal para datos sensibles que solo necesitas mientras el usuario interactúa activamente con la app en una sesión sin refrescar.

Recomendación para Principiantes

Para esta clase, usamos `localStorage` por simplicidad para entender la persistencia. Pero es vital que entiendan:

  1. NUNCA usar `localStorage` para tokens reales en producción.
  2. La forma estándar y segura para sesiones es usar **Cookies `HttpOnly` y `Secure`**, gestionadas por el servidor.
